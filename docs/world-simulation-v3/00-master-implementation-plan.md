# Sagadyssey 世界模拟 v3：总实施计划

## 0. 本文的地位

本文是从当前代码继续开发时的总装配计划。它不推翻 `world-simulation-v2` 对人物、产权、知识、交易、家庭、制度和战斗的领域设计，而是补上 v2 尚未落地的行为执行主干，并重新安排实现顺序。

发生冲突时遵守以下优先级：

1. 物品、人物、权利和订单不能复制或静默丢失；
2. 服务端真相与角色所知必须分离；
3. NPC 每次静止、拒绝、等待或改道都必须有可追踪原因；
4. 新模块只能通过稳定接口接入，不能继续向 `NpcBase` 堆条件分支；
5. 玩家界面服从角色知识，测试工具才能查看后台真值；
6. 视觉表现不能伪造尚未发生的生产、交易或社会关系。

## 1. 当前判断

当前工程不是“功能太少”，而是“领域系统已经很多，但行为执行仍由一组同优先级 Goal 竞争”。

现状包含：

- 稳定人物标识、生活档案、家庭、合同、制度、市场、生产批次、物流、权利与原子转移；
- 农民、工人、铁匠、商人、运输员、医师、士兵等实体 Goal；
- 玩家知识投影、交易谈判、阵营发现、验收快照和固定场景工具；
- 大量单元测试及旧存档夹具。

但还缺少：

- 统一的候选任务生成；
- 具体计划而非笼统 `WORK` 的承诺；
- 资源、工作站和目标的统一预留；
- 工作完成、受阻、等待和转入生活行为的标准状态机；
- 从领域需求自动形成生产/运输任务的桥接层；
- 可扩展的角色与活动注册方式；
- 对“NPC 为什么站着”的实时解释。

因此不整库重写。保留成熟领域服务，重写 NPC 行为编排层，并通过兼容适配器逐个替换旧 Goal。

## 2. 目标体验

### 2.1 玩家体验

玩家观察到的是一个有局部知识和真实物资流的世界：

- 农民没有成熟作物时会修工具、搬运收成、吃饭或拜访邻居，而不是永久站桩；
- 铁匠缺煤时会形成采购或运输需求，不会继续播放虚假锻造动作；
- 商人携带真实库存，只根据自己知道的价格和风险行动；
- 教会成员会举行仪式、记录婚丧、教学、救济和管理真实财产；
- 阵营、机构、家庭和职业是相互重叠的社会关系，不是一个万能标签；
- 玩家通过交谈、观察、文书和关系逐步了解世界，而不是打开后台面板。

### 2.2 测试体验

测试者可查看：

- 当前计划、步骤、目标、地点和期限；
- 本轮全部候选计划、分数、硬性淘汰理由；
- 资源和工作站预留；
- 阻塞原因、请求链、负责主体和重试条件；
- 最近计划切换、取消、超时与寻路失败；
- 玩家知识投影与后台真值的差异；
- 物品、生产批次和运输订单的因果链。

## 3. 不做的事情

- 不让一个全局 AI 知道全世界精确库存和价格；
- 不用随机动画伪装生产；
- 不让所有居民都成为玩家的直属单位；
- 不用一个“幸福值”控制全部社会行为；
- 不在首批实现宗教神迹、神力技能树或现代化统一银行；
- 不同时运行旧职业 Goal 和新计划执行器处理同一任务；
- 不因重构删除旧存档字段或研究数据。

### 5.2 主观决策上下文

`NpcDecisionContext` 只能包含该角色能够感知、记得或从可信来源得知的信息：

- 自身身体、需求、背包、装备和已承诺计划；
- 当前看见或听见的附近实体与危险；
- 已知家庭、朋友、雇佣和机构义务；
- 已知住宅、工作地点、市场、仓库与道路；
- 已知请求、订单与期限；
- 角色相信的价格、库存、阵营和事件，不直接读取全局真相；
- 管理员调试信息单独装配，绝不传入普通玩家载荷。

### 5.3 候选计划

所有行为模块实现同一接口：

```java
public interface NpcActivityProvider {
    ResourceLocation id();
    List<NpcActivityCandidate> propose(NpcDecisionContext context);
}
```

首批 Provider：

1. `EmergencyActivityProvider`：灭火、逃离、战斗、救援；
2. `NeedActivityProvider`：进食、治疗、睡眠；
3. `CommitmentActivityProvider`：继续已接受的订单、合同、约定；
4. `ProfessionActivityProvider`：农业、采集、锻造、运输、巡逻；
5. `HouseholdActivityProvider`：供给、照料、家务、回家；
6. `InstitutionActivityProvider`：议事会、行会、教会等机构职责；
7. `SocialActivityProvider`：交谈、拜访、传递消息；
8. `LeisureActivityProvider`：酒馆、阅读、观察、散步；
9. `AmbientActivityProvider`：短时等待、环顾、坐下。

候选计划包含：

- 唯一候选标识和模块标识；
- 具体对象、目标地点和受益人；
- 前置条件和硬性禁令；
- 预期收益、风险、时间、体力和机会成本；
- 所需物品、工作站和权限；
- 最迟开始、预计结束和重新评估时间；
- 成功、受阻、失败后的建议后继计划；
- 供测试者阅读的解释，不向普通玩家直接披露。

### 5.4 选择与承诺

选择顺序不是简单 Goal 优先级，而是：

1. 过滤死亡、权限不足、地点未知、资源不可用等硬性条件；
2. 对剩余候选计算角色主观效用；
3. 对相似候选加入边际递减，避免重复同一活动；
4. 使用带噪声的有限理性选择，而不是全知最优；
5. 对选中候选创建具体 `NpcPlanId`；
6. 在计划锁定期内只允许合法的紧急抢占；
7. 抢占时必须调用执行器取消并释放全部预留。

旧 `NpcAgencyDecision` 以 `Action.WORK` 为键的承诺过粗。迁移后承诺键必须至少包含 Provider、计划类型、目标和订单；旧类只作为分数因子的兼容实现，不能继续决定多个不同工作 Goal 的共同锁定结果。

### 5.5 计划状态机

```text
PROPOSED
  → SELECTED
  → RESERVING
  → TRAVELLING
  → ACTING
  → SETTLING
  → SUCCEEDED

任意可恢复步骤 → BLOCKED → WAITING → RESERVING/TRAVELLING
任意不可恢复步骤 → FAILED
授权撤销/紧急抢占/目标消失 → CANCELLED
```

状态规则：

- `RESERVING` 预留物品、容器、工作站、床位或交谈对象；
- `TRAVELLING` 只负责移动，不产生工作结果；
- `ACTING` 才能产生进度和动画；
- `SETTLING` 使用已有 `ProductionService`、`TransferService` 和权利服务提交结果；
- `SUCCEEDED/FAILED/CANCELLED` 必须释放预留并写审计；
- `BLOCKED` 必须携带结构化原因与解除条件；
- 服务端重启后只能恢复幂等步骤；不能确定是否已结算时进入人工核对，而不是再执行一次。

### 5.6 静止也是计划

合法静止行为包括：

- 在工作站等待已接单运输；
- 守卫固定岗位；
- 坐下休息；
- 排队使用工作站；
- 等待仪式或会议开始；
- 与另一个角色交谈；
- 短时观察工作对象。

所有合法静止必须包含地点、原因、开始时间、到期时间和超时方案。加载实体在非睡眠状态下连续 200 tick 没有计划，也没有明确阻塞记录，视为错误并进入调试告警。

### 5.7 中断矩阵与原子边界

中断不能由每个执行器自行猜测。调度器统一执行以下规则：

| 事件 | 默认处理 | 预留处理 | 恢复方式 |
|---|---|---|---|
| 发现迫近危险 | 暂停非紧急计划并转入逃离/战斗 | 工作站和材料短期保留；超时后释放 | 危险解除后重新验证原计划 |
| 严重饥饿或伤势 | 完成当前原子步骤后暂停 | 释放交谈对象和移动目标，保留已领取物品归属 | 需求降低后重新生成候选 |
| 班次结束 | 不打断当前实体交互，完成结算后停止下一循环 | 正常释放 | 转入家庭、个人或休息计划 |
| 新玩家命令 | 先验证权限；普通命令排队，紧急合法命令可抢占 | 被取消计划必须正式释放 | 生成带发出者和期限的新候选 |
| 目标消失或寻路失败 | 进入 `BLOCKED`，记录失败次数和重试时间 | 释放失效目标；工作站只在短退避期保留 | 重试、改道或选择替代计划 |
| 区块卸载 | 在安全点写 checkpoint，停止实体方块操作 | 资产预留转为可持久验证的语义预留 | 加载后先对账再恢复 |
| NPC 死亡 | 计划取消并结算死亡后果 | 释放任务预留；随身资产走死亡/继承规则 | 不恢复原计划 |
| 服务端停止 | 写入最后已提交步骤与容器修订号 | 保留可恢复预留 | 启动时幂等验证 |

以下操作视为不可分割原子边界：一次方块状态修改及其产物登记、一次 `TransferService` 提交、一次 `ProductionService` 完成/取消、一次订单状态转换。中断只能发生在原子边界之前或之后，不能出现“原料已扣、产物未登记”的半状态。

### 5.8 调度触发

不逐 tick 重算全部候选。以下事件触发立即或短延迟重算：

- 当前计划结束、失败、受阻或被取消；
- 饥饿、疲劳、伤势或危险越过阈值；
- 班次改变；
- 新订单、资源到货、工作站释放；
- 玩家提出命令、合同或交易；
- 家庭或机构发出义务；
- 目标人物、地点或资产状态改变。

另有按实体 UUID 错开的 100–200 tick 兜底复核。传感器采用缓存和空间索引，禁止每个 NPC 每 tick 扫描大范围方块、容器或全体居民。

## 6. 工作、需求与物流闭环

### 6.1 领域对象

新增或统一以下对象：

- `NeedRequest`：需要什么、多少、品质、送到哪里、为什么、何时前需要；
- `WorkOrder`：谁提出、产出归谁、配方、输入、工作地点、报酬和期限；
- `ProductionBatch`：一次已经预留输入的真实生产；
- `LogisticsOrderRecord`：把已存在资产从一处运到另一处；
- `WorkstationReservation`：在一段时间内占用工作站；
- `AssetReservation`：防止同一物品同时被消费、交易和生产。

`NeedRequest` 的状态：

```text
OPEN → MATCHED → IN_TRANSIT → DELIVERED → CONSUMED/CLOSED
  └→ WAITING_EXTERNAL
  └→ UNREACHABLE
  └→ CANCELLED
```

### 6.2 工作结束流程

每种职业统一执行：

1. 完成当前动作；
2. 提交生产或采集结果；
3. 将产物存入合法容器或个人携带区；
4. 归还借用工具和剩余原料；
5. 释放工作站、目标和资产预留；
6. 更新订单和领域事件；
7. 触发重新计划；
8. 有下一订单则继续，没有则选择维护、物流、家庭、社会或休闲计划。

### 6.3 三个首批职业

#### 农民

- 观察成熟作物、可播种地、种子、工具和季节；
- 工作包括收获、播种、耕地、灌溉、搬运、留种和工具维护；
- 没有成熟作物不是故障，应转为搬运、维护或生活计划；
- 收成归属由土地、合同和家庭规则决定，不自动归玩家。

#### 工人

- 从明确工作区和订单选择采集/施工目标；
- 不再为了“找活”无限随机探索；
- 工作区无有效目标时形成完成或阻塞结论；
- 临时脚手架必须预留、放置、回收并通过守恒检查。

#### 铁匠

- 只处理真实维修单和生产订单；
- 缺铁、煤、工具、存储空间或工作站时创建具体请求；
- 每件产品有输入所有者、输出所有者和劳动义务；
- 锻造动画只在 `ACTING` 阶段播放一次完整循环；
- 完成后执行结算和交付，不立即无条件重复相同动作。

### 6.4 请求完整性

物资请求不能在每次扫描时重复创建。请求幂等键至少包含：请求主体、用途/订单、物品规格、目标容器和有效时间窗。

- 同一幂等键存在 `OPEN/MATCHED/IN_TRANSIT` 请求时只更新需求量，不新建请求；
- 允许部分履约，记录原数量、已预留、在途、已交付和剩余数量；
- 请求具有到期时间、最大重试次数和取消理由；
- 请求依赖形成有向图，新增边时检测自环和循环依赖；
- 检测到循环时不继续生成物流单，而是标记 `BLOCKED_CYCLE` 并上报测试者；
- 外部确实无货时进入 `WAITING_EXTERNAL`，不得每 20 tick 重建订单；
- 订单取消、容器销毁或所有权变化时，已预留资产必须重新核验并释放或改派；
- 工作输出存放由订单的 `OutputDispositionPolicy` 决定，禁止继续按物品类型猜测“这是公共产物还是私人财产”。

## 7. 更多 NPC 的扩展方式

### 7.1 不继续扩充职业枚举

现有 `NpcProfession` 暂时保留，作为旧存档、属性和网络序号兼容层。新增人物能力使用数据驱动定义：

```text
RoleDefinition
├── id
├── display_name
├── activity_providers
├── skills
├── permitted_workstations
├── equipment_preferences
├── schedule_template
└── appearance_tags
```

人物可同时拥有：

- 一个或多个谋生角色，如农民、抄写员、运输员；
- 家庭角色，如家长、受照料者；
- 机构成员资格；
- 机构职位及其权限；
- 临时合同或任务角色。

角色不直接赋予财产所有权，也不自动使人物服从玩家。

### 7.2 注册接口

新模块只能通过注册器接入：

- 注册角色定义；
- 注册活动 Provider；
- 注册执行器；
- 注册语义工作站/建筑设施；
- 注册知识投影与对话主题；
- 注册调试渲染器；
- 注册 GameTest 场景。

主类不再为每种新 NPC 手写一串 Goal 和网络包。

## 8. 教会与宗教机构工作流

教会模块与行为内核并行设计，在接口稳定后接入。详细设计见
[《教会、宗教机构与 NPC 模块》](./church-institution-and-npcs.md)。

必须区分：

- `sagadyssey:church`：跨地区广义阵营及政治关系；
- 本地教堂/修院：拥有具体章程、成员、职位、财产和管辖范围的 `InstitutionRecord`；
- 神职身份：人物的成员资格和职位；
- 谋生技能：教学、抄写、治疗、烹饪等角色能力；
- 信仰与声望：人物主观状态和社会评价，不能代替权限。

首批角色：

1. 神职主持者：主持日常仪式、接待居民、记录重要事件；
2. 执事/管事：管理捐赠、救济库存、采购和建筑维护；
3. 修士或修女：耕作、抄写、照料病弱、执行共同生活日程；
4. 抄写员/教员：保存文书、教学、传播或纠正消息；
5. 墓园或教堂看守：维护场所、处理丧葬设施。

首条纵向切片：

```text
家庭粮食不足
→ 家庭成员向本地教堂求助
→ 执事检查真实救济库存和资格
→ 形成可审计的救济决定
→ 运输/当面交付真实食物
→ 家庭需求下降、教堂库存减少
→ 事件被见证者记忆并影响关系
```

第二条纵向切片是定时公共仪式：人员收到消息、前往教堂、容量与主持者条件满足后开始；参与改变关系和共享知识，但不凭空产生物资或全局加成。

## 9. 玩家命令、日程和自主性

### 9.1 命令不是永久状态机

`NpcCommand.WORK/FOLLOW/STAY/PATROL` 在兼容期保留，但只生成“命令候选”或约束，不再直接开启一组 Goal。

命令必须包含：

- 发出者；
- 权限证据；
- 目标和范围；
- 开始、到期和取消条件；
- 可接受风险；
- 与既有义务冲突时的处理方式。

### 9.2 日程是承诺窗口

现有 `NpcSchedulePlanner` 的 `WORK/PERSONAL/REST` 可作为兼容输入，但新日程由多个有地点和期限的承诺块组成：

- 睡眠窗口；
- 工作班次；
- 固定仪式、会议或授课；
- 家庭照料；
- 个人自由时间。

日程只影响候选权重和合法时间，不直接告诉实体播放什么动作。紧急状态可抢占，但会产生迟到、失约或中断记录。

## 10. UI 与信息边界

### 10.1 普通玩家

普通玩家界面只展示角色能够合理观察或得知的内容：

- 外观、动作、公开身份；
- 对方愿意透露的工作、家庭和机构信息；
- 对方愿意交易的真实资产；
- 玩家已经发现的阵营与关系；
- 模糊、可能过时或带来源的信息。

不能展示：精确候选分数、隐藏背包、全局库存、未知阵营、完整关系网和后台阻塞代码。

### 10.2 测试者

新增只读观察页或命令：

- `/saga npc brain inspect <target>`；
- `/saga npc brain history <target>`；
- `/saga npc brain reservations <target>`；
- `/saga npc brain requests <target>`；
- `/saga npc brain watch <target> [seconds]`。

这些入口需要管理员权限或显式测试模式，不改变世界状态。现有 verifier 快照增加计划、请求和预留计数，但保持快照命令只读。

## 11. 旧科技点系统停用

旧 Research/科技点系统与当前“从社会、知识和物资关系中形成能力”的方向冲突，立即进入冻结状态：

- 不再注册 K 键；
- 不再开放研究 GUI；
- 不再注册玩家研究命令；
- 不再因成就奖励研究点；
- 不再允许研究解锁网络请求；
- 保留 Attachment 类型和旧数据读取，保证存档可加载；
- 保留旧类和资源文件，集中加弃用说明，不大段删除代码；
- 网络协议若为兼容而继续登记，处理器必须只返回“功能已停用”，不能改变数据；
- 后续能力解锁改由知识、训练、师徒、机构资格、工具和真实资源共同决定。

只有在至少一个稳定版本验证旧存档迁移后，才讨论彻底删除旧代码。

## 12. 迁移与双轨策略

新增每世界行为模式：

```text
LEGACY    旧 Goal 行为
PLANNED   新计划内核
```

规则：

- 单个 NPC 在任何时刻只能属于一种行为模式；
- 开发测试世界可全局启用 `PLANNED`；
- 旧世界默认保持 `LEGACY`，管理员先运行 dry-run；
- 支持按 NPC/聚落灰度迁移，但同一 NPC 不能双跑；
- 回滚只切换执行模式，不回滚已经合法提交的物资和历史；
- 新计划状态使用独立 schema 版本；
- 旧 `NpcProfession`、命令和工作地点通过适配器读取；
- 数据迁移必须生成物品、订单、计划和人物数量报告。

## 16. 自动化测试矩阵

每阶段至少覆盖：

| 类型 | 断言 |
|---|---|
| 单元测试 | 候选过滤、评分、状态转换、权限、超时和取消 |
| 属性测试 | 任意中断点下资产总量和预留唯一性 |
| 持久化测试 | 计划、请求、订单重载后不重复提交 |
| GameTest | NPC 到达地点、执行一次动作、真实结算并离开 |
| 多 NPC 测试 | 竞争工作站、容器最后一格、最后一批原料 |
| 多人测试 | 不同玩家权限和知识投影不同 |
| Soak 测试 | 三至十个游戏日无无限循环、任务泄漏和库存漂移 |
| 性能测试 | 每 tick 规划、感知、寻路和网络字节预算 |
| 迁移测试 | 旧世界人物、物品、合同、阵营和 Research 数据可加载 |

核心不变量：

1. 物品守恒；
2. 一个资产同一时刻只有一个互斥预留；
3. 一个 NPC 同一时刻只有一个主计划；
4. 每个计划终态都会释放预留；
5. 每个实体动作都对应计划步骤；
6. 普通玩家载荷不泄露后台真值；
7. 所有静止超过阈值的 NPC 都有可解释状态；
8. 旧模式和新模式不会同时结算同一工作。

## 17. 人工游戏验收主线

### 17.1 工作闭环

1. 生成一个铁匠和真实工坊；
2. 给出一张维修单，但不提供煤；
3. 观察铁匠报告阻塞并创建请求，不播放锻造循环；
4. 让运输员送达煤；
5. 观察铁匠恢复、完成、结算、交付；
6. 观察其选择下一订单、维护或生活计划；
7. 对比前后 verifier 快照确认守恒。

### 17.2 社会与教会闭环

1. 创建库存不足的家庭与有少量救济粮的教堂；
2. 家庭成员通过交谈或关系得知可以求助；
3. 执事依据真实库存、章程和申请情况作出决定；
4. 食物被真实转移并形成账簿和见证记忆；
5. 普通玩家只从观察/交谈得知部分事实；
6. 测试者查看完整因果链；
7. 制造库存不足或偏袒案例，验证拒绝与争议。

## 18. 每阶段完成定义

一个阶段只有同时满足以下条件才算完成：

- 设计差异已写入文档；
- 所有新增领域对象有 schema 与迁移规则；
- 自动化测试通过；
- `gradlew build` 通过；
- 游戏内主流程已人工测试；
- 保存并重载后结果一致；
- 普通玩家和测试者信息边界经过检查；
- 性能指标没有超过该阶段预算；
- 已知问题和回滚办法已记录；
- 不存在为了演示而绕过真实物资或权限的临时代码。

## 19. 立即执行顺序

1. 完成阶段 0：停用旧科技点入口并保留存档兼容；
2. 冻结 `NpcActivityProvider`、`NpcPlan`、`NpcTaskExecutor` 三个公共接口；
3. 写纯 Java 状态机测试；
4. 接入只读调试命令；
5. 以铁匠为第一个完整迁移对象；
6. 确认三日循环、重启和物品守恒后再迁移农民与工人；
7. 同期只开发教会领域模型和数据定义，不抢先直接修改 `NpcBase`；
8. 行为接口稳定后接入教会救济纵向切片。

在第 5 步通过之前，不增加更多职业动作；在第 7 阶段通过之前，不把教会做成只提供按钮、Buff 或无限商品的装饰阵营。

## 20. 同类模组对照后的取舍

- MineColonies：借鉴明确的物资请求和物流依赖，不复制集中式殖民地所有权；
- Millénaire：借鉴数据驱动拜访、聚落盈余/短缺和有意义的空闲活动，不把人物生活完全写死为文化脚本；
- TekTopia：借鉴住宅、酒馆、图书馆等实体地点行为和真实需求门控，不用单一幸福值决定全部行为；
- MCA Reborn：借鉴家庭、关系和感知/任务分层，不让对话系统代替真实生产与资产流。

本计划的最终选择是：以已有领域模拟为真值，以统一计划内核连接实体行为，以可恢复的任务状态机保证正确性，再用数据驱动角色扩展更多 NPC。
